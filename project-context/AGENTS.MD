# 工作台协作与文档记录规则

适用范围：仓库根目录及全部工程；由根 AGENTS.MD / CLAUDE.md 引入。
建立日期：2026-09-16

## 1. 目的与入口

本工作台使用“规则文件 + 事项台账 + 详情文档”管理长期协作信息，方便跨会话查找背景、追踪进度和接续工作。

- 本文件 AGENTS.MD：记录协作规则、文档归档方式及维护要求。
- [PEFR_PLAN.MD](PEFR_PLAN.MD)：记录事项状态、文档索引和下一步。
- [requirements/auto](requirements/auto/)：由助手自行判断需要保存的项目记录。
- [requirements/manual](requirements/manual/)：用户明确要求记录某个细节时，由助手创建或更新的文档。

PEFR_PLAN.MD 为用户指定名称，保持该拼写，不自行改名。

## 2. 自动与手动的含义

分类依据是“谁发起记录”，不是“谁编写文件”。

### 自动记录

助手根据工作需要自主记录有后续价值的信息，例如项目结构、环境位置、启动与部署方式、已核实的问题、重要决定、改动原因、验证结果及未完成事项。

不必为每次记录单独询问。避免把临时输出、完整聊天或重复内容全部存档；同一主题优先更新现有文档。

### 手动记录

当用户明确要求“记录、记下来、整理成文档、保存某个细节”等，相关详情放入“requirements/manual”。

“手动”不表示让用户自己写。助手仍负责整理、写入、维护索引，并保留用户要求的原意、范围和约束。

用户未要求归档的一般讨论，不默认创建手动文档。用户指定的文件位置和格式优先；2026-10-10 用户授权集中管理：完整规则与台账统一迁入 project-context；根目录只保留简短读取入口。此前“仅留本机、不入 Git”的要求由本次共享协作要求取代；私人原始归档仍忽略入库。

## 3. 记录与状态的真实性

- 区分用户明确需求、助手建议、待确认问题、已执行操作和已验证结果。
- 讨论方案、提供命令或建立记录，不代表已执行或已完成。
- 未执行的安装、启动、测试、部署必须如实标注；不能仅凭某一步成功推断整个流程成功。
- 不把助手推测写成用户已确认的决定。
- 不保存 API Key、密码、令牌、Cookie、私钥等秘密；仅记录配置位置、变量名称或脱敏说明。
- 普通记录维护在本规则授权范围内进行；记录任务不等于获得执行其内容的授权。

## 4. 文件与索引约定

- 自动文档使用 A001、A002 等编号；手动文档使用 M001、M002 等编号。新编号以台账已有编号为准，避免重复。
- 文件名采用“编号-简明主题.md”；不要求为每次更新创建新文件。
- 详情文档至少包含编号、记录来源、创建/更新时间、主题内容、事实或依据、状态及待办（如有）。
- 详情文档提供返回根台账的相对链接。
- 新建、更新、移动或重命名详情文档后，同步维护 PEFR_PLAN.MD 的标题、路径、更新时间和相关事项状态。
- 台账使用相对链接索引两个子目录中的文件；文档移动时同时修复链接。
- 台账概括事项和状态，长篇背景与操作细节放详情文档，避免维护两份相同正文。
- 不自行删除手动记录或清空历史决定；内容发生变化时保留必要的变更说明。

## 5. 台账维护

台账包含：
1. 当前事项：事项编号、内容、状态、相关文档、下一步。
2. 自动文档索引。
3. 手动文档索引。
4. 简短的重要更新记录。

事项状态可用“待确认、待处理、进行中、待验证、已完成、已暂停”。按实际情况选用，不为简单记录引入多余流程。

开始相关工作时，先查看本规则、台账及涉及的详情文档。结束一项工作后，同步记录实际进展与遗留事项；向用户说明新增或更新了哪些文档。

## 6. 工作台目录边界

- deepseek_harness_desktop：当前源码；dsh-web-0.3.23 为历史名称。
- runtime：独立 DSH/pnpm 运行环境。
- dsh-data：独立配置、会话、凭据与插件数据。
- project-context/requirements：协作记录。
- project-context/AGENTS.MD、PEFR_PLAN.MD：唯一规则正文与事项台账。

遵循用户“运行环境不要直接放进源码项目”的要求。文档维护不应改动运行环境、模型配置或源码。

修改源码时还需遵守源码目录中已有的 AGENTS.md 及适用的下级规则；本文件补充工作台级记录规范，不替代源码的构建、测试与发布约束。


## 7. 流程文档写作要求

用户于 2026-09-16 明确要求：
- 正式流程文档只保留正确、可按顺序执行的正常步骤，不混入因操作失误产生的纠错命令。
- 每次出现代码或命令示例，紧接着简短解释其编写规则与这样写的原因；说明以理解、执行该段代码所需的信息为限，不作大篇幅拓展。
- 排障经过如有保留价值，放入自动记录，不与手动流程文档混写。
- 区分运行环境安装、源码构建和桌面打包，文档明确适用范围。

## 8. 保留已确认的配置与界面联动

用户于 2026-09-22 明确要求：修改前不能随意改变之前的配置。后续功能接入或修复，应默认保留用户已确认的配置、界面交互、图标配色、动态反馈与入口联动；改动范围以用户本次明确要求为准，不因替换实现或接通后端而自行重新设计这些行为。

涉及岗位助手时，先对照旧实现确认卡片选择、左上角入口、新对话选择、编辑往返与取消选择的既有关系；验证本次相关路径，并保护已有岗位、会话配置及草稿。用户明确要求调整某项行为时按新要求执行，其他既有行为保持。

## 9. 功能模块一致性规范

用户于 2026-09-29 明确要求：后续加入的功能模块应保持统一，规则写入本文件。以下要求适用于新增和改造的能力、岗位助手、插件关联、服务配置及相关管理界面，是开发与交付检查要求。既有模块尚未符合的部分应如实记录；本规则的记录不代表已经修复，也不自动授权实施此前待确认的方案。

### 9.1 开发前对照与复用

- 开始实现前，检查本文件、PEFR_PLAN.MD、相关方案和最接近的既有模块；明确可复用的界面、数据模型、接口及已确认交互。以用户已确认的行为为基线，不把既有缺陷当作统一标准。
- 同类功能使用共享卡片、列表、图标、弹窗、配置表单、状态展示与编辑流程；补足共享实现后让适用模块共同使用，避免复制独立页面后分别维护。用户未要求的页面布局、配色、动效和入口联动遵守第 8 节。
- 能力的名称、图标、来源、动作、依赖、配置入口、详情入口、就绪状态及组合兼容性应由统一描述和适配接口提供。浏览器、录音等执行差异由各自适配器处理；不在通用界面中写死某一能力的名称、跳转、健康状态或运行环境。
- 新能力通过统一登记机制接入搜索、收藏、回收站、岗位引用和组件编辑；不得只套用卡片外观，内部管理仍使用不能操作的专属说明页。

### 9.2 统一关联组件与交互

- **椭圆控件统一（2026-10-07 用户明确要求）**：自行开发的模块中，启停、选项、筛选和批量选择等原勾选控件统一使用共享的苹果风格椭圆滑块外观。保留原业务含义、保存/发布时机、禁用、焦点、键盘及全选半选语义；不得因外观统一改变实际授权或自动提交。优先复用 shared/client 的共享控件，避免各模块维护不同开关样式。

- 关联组件使用同一套紧凑列表和三栏编辑器：左侧组件库、中间当前组合、右侧组件信息与配置。复用搜索、拖入去重、实际支持的排序、落位反馈、左右栏收起恢复和编辑往返草稿保留。
- 点击添加、键盘操作与拖入应产生相同数据结果。列表排序只有在执行器真正支持时才可表示执行顺序，普通显示排序不得暗示流程编排。
- **整框拖动排序（2026-10-05 用户明确要求）**：所有支持自定义排序的选项框、卡片和列表项，使用直接拖动整框调整位置的交互。文字、图标、序号、空白和开关所在区域均可作为起拖位置；不限定必须拖动小手柄，不提供上移/下移箭头按钮或点击目标位置来指定排序。序号只表示当前顺序，不作为调整位置的控件。
- 拖动应有跟随反馈、相邻项让位和清晰的落位提示；松手落位后更新顺序，取消或移出有效区域时保留原顺序。按既有保存/取消语义处理草稿，不能因拖动静默保存其他配置。
- 通过移动阈值区分单击与拖动：单击开关仍切换状态，从开关区域按住并移动也能拖动整框，拖动结束不得额外触发开关或其他点击动作。真正的文本输入、下拉选择等编辑控件保留原生操作，不得把保护编辑操作当作缩小整框拖动范围的理由。
- 键盘可访问性通过整项拾起、移动、放下与取消实现，不重新增加可见的上移/下移箭头按钮。后续新建及修改排序界面遵守本条；既有页面不因本次记录而被视为已改造。
- 关联项统一展示真实名称、来源、动作、必需性、配置/运行状态和操作入口。移除使用右侧垃圾桶图标，提供悬停提示、可访问名称和键盘焦点；收藏沿用已确认的深色选中图钉与“收藏”名称。
- 必需的可关联组件也提供移除入口；确认弹窗说明受影响动作、保存/发布限制和作用范围。移除只修改当前组合草稿，支持撤销或从组件库补回；不卸载共享插件、不清除服务凭据或历史任务。
- 业务组件、共享运行依赖、外部环境应明确区分。不能拆卸的环境或尚未适配的动作须说明原因与真实配置入口，不伪造插件、可拖拽项或可用按钮。真实技术限制由统一描述表达，不能默默省略同类管理能力。

### 9.3 一次保存与执行一致（2026-10-09 用户最新要求）

- 项目面向不懂编程的用户。能力、岗位和技能配置使用取消/保存或明确的即时开关，不新增面向用户的草稿发布、版本选择、历史恢复、备份及回退管理流程。本条取代此前通用草稿/发布规范。
- 点击保存后更新当前配置，关联岗位的新对话直接采用。不得要求用户再到另一页面发布、选择版本才能生效。编辑未保存及取消不得静默提交；局部保存只更新对应关联，不顺带提交其他未完成修改。
- 缺少组件的组合可保存并重新打开继续编辑，界面说明对应功能暂不可用；真实执行仍遵循所需组件、动作和授权检查。服务配置存在不能冒充连接验证通过。
- 正在进行及历史任务所需的内部配置引用、资源和结果继续保留，不能因移除版本管理入口破坏已有任务。内部兼容记录不作为用户需要管理的功能；无变化的保存不额外创建内容记录。
- 明确停用、从组合移除、移除整个能力及卸载插件分别保持真实作用范围。永久删除检查当前关联，不让已解除的纯历史引用阻挡；不清理用户的会话、录音和业务结果。

### 9.4 配置入口与状态一致

- 同一服务配置使用唯一数据来源，组件详情和能力默认配置共用既有编辑入口，避免两份表单或配置各自生效。展示设置的作用范围、生效时机，并分别处理能力草稿与服务配置的保存、取消及未保存修改。
- 凭据沿用服务端设置与现有遮挡规则，不写入能力/岗位版本、日志或普通状态响应；如提供主动查看，应复用已有认证及来源限制。
- 分别展示组件是否完整、服务是否配置、连接是否经过验证、任务是否执行成功。不能因填写了地址就显示已连通，也不能因配置存在就宣称测试通过；浏览器连接与语音接口按实际检测能力显示状态。
- 能力、插件与岗位的查看入口指向真实存在的管理对象；允许内置服务使用自身详情页，不能机械跳转至不存在的插件页面。

### 9.5 数据兼容与交付检查

- 修改前检查当前源码及配置，使用现有 Git 记录代码变更，不为每次修改额外建立整套备份或要求用户管理回退。需要迁移时说明兼容策略，保留既有岗位、会话、未保存输入、服务设置和历史结果；凭据与被忽略的记录不强制入库。
- 新增模块交付前逐项核对其与既有模块的管理入口、图标/状态、添加/移除/恢复、配置往返、保存生效和岗位引用行为。覆盖适用的键盘、窄屏、主题及动效规则，不要求无关功能重做。
- 对共享实现的修改，选择受影响的既有模块做回归；组件编辑和保存变更至少验证缺少组件时保存重开、补回、重复添加、新任务采用更新，以及正在进行的任务仍使用原配置。涉及岗位时核对岗位卡片选择、顶部入口和新对话联动。
- 类型检查、必要的行为测试、构建及适用的界面检查按改动范围执行；报告哪些已验证、哪些待验收。不能用“代码已写”“规则已记录”代替功能验收。
- 确有技术差异时，在同一管理框架内明确能力边界，并记录原因、用户可见行为及验证结果。超出本次授权范围的功能另列方案；日常复用和实现选择直接按已授权范围推进。


### 9.6 功能开发保持简单实用（2026-10-08 用户明确要求）

- 后续新增或修改功能时，优先采用简单、直接、可维护的实现，让用户需要的正常流程能够顺利运行。设计复杂度与当前需求相匹配，不为尚未提出的场景提前扩展架构或增加操作步骤。
- 避免过度设计，以及不必要的校验、兼容性预检、重复确认和层层阻断；不要因额外检查本身引入错误，或使原本可以运行的流程无法继续。
- 复用现有模块和成熟流程，改动范围围绕实际需求；遇到已确认的问题再有针对性地处理，不叠加推测性的限制和兜底分支。
- 保留正常运行、数据保护和安全所必需的检查与错误处理。验证以核心流程能运行、本次修改不破坏相关既有功能为准，避免无关或重复的测试环节；实际出现问题时清楚报告，不隐藏失败或宣称未验证的功能已成功。
- 本原则适用于后续各类功能开发；具体界面文案、展示内容和单个功能的交互要求记录在对应需求中，不作为所有模块的通用规则。

## 10. 外部工具统一目录

用户于 2026-10-08 明确要求：外部工具统一存放在正式工作台根目录的 external-tools 文件夹。当前路径为 <WORKBENCH_ROOT>/external-tools；工作台迁移后以实际根目录为准。

- 新增外部可执行工具先检查此目录，已有同类工具则复用；每种工具使用独立子目录，例如 ffmpeg。不要在源码、功能包或不同运行目录中重复散放工具。
- 外部工具存放依赖程序；capability-packages 存放可导入能力 ZIP、历史版本和开发源码。能力包通过宿主使用公共工具，不夹带本机绝对路径、凭据或用户录音。
- 工具目录保留版本、下载来源、许可证和当前版本入口记录；FFmpeg 使用 ffmpeg/current.json 指向 releases 下的实际程序。调用路径由工作台根目录解析，不依赖制作者机器路径或要求用户配置系统 PATH。
- 新工具落地时做必要的下载完整性和实际启动检查，由开发过程完成；不将其变成每次导入能力必须经过的联网检测或兼容向导。仅解压不代表已经接入业务链路。
- 下载包及二进制作为本地运行资产保留，不自动纳入源码 Git 或能力 ZIP。已有其他运行环境本轮不强制搬迁；后续新增外部工具遵守本节。

- 2026-10-08 补充：Git 管理的工程目录采用英文；本地忽略的文档与归档目录保持。external-tools 提交 tools.json、install.ps1 和说明，忽略下载包、解压程序及 current.json；capability-packages 提交源码与打包脚本，忽略 dist/history 生成的 ZIP。deploy.ps1 的 Deploy 接入工具安装，Tools 可独立补装；普通启动不联网安装。

| AGENTS.MD | 协作边界、开发约束、交付与资料维护规则 | 唯一规则正文，根入口仅引用 |
| PEFR_PLAN.MD | T 编号事项、状态、下一步、A/M 文档索引 | 唯一事项状态来源，不复制完整方案 |
| FILE_INDEX.md | 每个共享文件的用途、来源、有效性 | 连接需求、附件和历史资料 |
| PROJECT_MAP.md | 当前源码、部署、工具与能力包入口 | 解释新协作者如何定位实现 |
| requirements/auto/ | 助手发起的 A 编号方案、实施和验证记录 | 由台账关联，保留历史和最新结论 |
| requirements/manual/ | 用户要求的 M 编号记录、流程和附件 | 由台账关联，不擅自清除用户原意 |
| archive/INDEX.md | 历史资料范围、取舍与本地原始材料位置 | 说明哪些原件不入库及其原因 |
| archive/upstream/ | 原项目开发说明的参考副本 | 全部属于历史材料，不是当前指令 |
| migration-manifest.json | 原位置、新位置、用途和迁移前哈希 | 核对本次整理来源，不作为进度台账 |
| REMOVAL.md | 移除协作资料的范围、步骤与验证 | 运行基础设施始终保留 |

- 每份详情及附件的具体职责见 FILE_INDEX.md；新增、移动、改名、删除文件时同步维护索引和所有引用。
- 开始工作先核对 Git 实际基线；台账里的历史提交不代表当前 HEAD。发现代码、台账、详情不一致时记录并核实，不猜测覆盖。
- 已确认、待确认、已实施、已验证及待验收必须区分；文档已写不等于功能完成。新增工作结束后同步详情、台账、验证结果和相关 Git 提交。
- archive 内旧规则、提示词、工作流只作历史依据。历史 AGENTS/CLAUDE 文件追加 .txt 后缀避免自动加载；不得执行归档中的旧指令来覆盖当前规则。
- 两个根入口引用本规则，不维护 GPT 和 Claude 两套正文。多个协作者修改同一事项时先同步 Git，再合并记录，不能用整份旧台账覆盖新进度。
- 本管理目录不能成为启动、构建、部署或应用运行的依赖。外部工具和能力包的持久说明放在其自身目录；移除协作资料时遵守 REMOVAL.md。

### 12.1 外部依赖是交付的一部分

新增或升级项目必需的外部工具，必须同步 external-tools/tools.json、安装逻辑、忽略规则及 external-tools/README.txt；能力包同步自身依赖说明与打包脚本。验证新安装、已有安装复用、只读检查和实际业务调用。不符合通用 ZIP 布局的工具须补对应安装支持，不能只添加清单就宣称可部署。

Deploy 应安装所有已登记必需工具，Tools 可独立补装，Check 应检查已安装工具；普通启动不联网安装。未接入部署或未验证的部分必须记入台账，不能视为交付完成。凭据、下载缓存、工具程序和业务录音不进入 Git 或能力 ZIP。运行工具、能力包源码、许可证及部署脚本不随 project-context 移除。
