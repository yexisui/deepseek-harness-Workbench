## 1. 最终要交付的体验

打开或拖入 DOCX → 在工作台左侧直接编辑 → 选中文字在右侧提问 → 可补充外部知识库依据 → AI 提出局部修改 → 查看原文与建议 → 采用 → 保存或另存为 Word。

文档解析、分页、人工编辑和保存都在本机。提问时，当前选区、必要上下文以及选用的知识库片段交给工作台已配置的外网模型 API。断网时可以继续人工编辑、保存；AI 功能需能连接所选 API。外部知识库按其实际地址和网络可达性使用。

首轮验收对象为 `.docx`。旧版 `.doc`、Excel、PPT、复杂修订与多人协作不算本轮编辑交付；需要时另做转换或专门支持。目标是尽量保留原格式，不能保证所有 Word 特性和分页完全一致。

## 3. 采用的组合与界面

**候选本机 DOCX 编辑器 + dsh-office-toolkit + 现有模型 API + 外部知识库适配器。**

- 编辑器：优先验证 `@docx-editor.dev/core`、`@docx-editor.dev/react` 2.28.0 开源部分，不引入其商业 pro、editor-api、docx-to-pdf 包。实际包与依赖许可、格式兼容和构建能力在 P0 验证。
- 文档修改：保留 dsh-office-toolkit 0.3.32。当前只公开插件入口，历史测试曾直接调用内部核心文件；正式接入需验证公开工具调用并封装适配，不把内部导入当成稳定 API。
- 模型：复用现有外网 API 与默认模型。保持服务端持有凭据，AI 输出结构化建议，由本地代码验证和执行。
- 知识库：接用户实际已有服务，只做所需检索与引用适配，不新建向量数据库或模型部署。具体服务未确定，不宣称通用地址即可兼容全部产品。

布局沿用参考图：顶部放文件名、打开、保存、另存为和保存状态；左侧约 2/3 为文档；右上显示选区、大纲或引用；右下为问答和修改建议。右栏可收起、宽度可调整，主界面沿用现有主题。Word 先支持原生文字和段落选区，扫描页矩形 OCR 属于后续工具范围。

编辑资源、样式、字体和 WASM 在本机提供。原项目使用自有插件加载/打包规则，P0 必须验证实际宿主集成，不能只用独立网页成功代替。

## 4. 能力中心如何组织

完整规划仍为 **5 个能力**。根据用户当前重点，**建议调整交付顺序，先完成“智能文档”和“知识库问答”两个能力**；此顺序是本轮建议，尚未代表其开发已获批准。

| 能力 | 功能范围 | 建议顺序 |
| --- | --- | --- |
| 智能文档 | DOCX 编辑、选区/全文问答、解释、摘要、AI 局部修改 | 本轮核心 |
| 知识库问答 | 外部检索、来源引用、在文档侧栏联合问答；也可单独用于岗位 | 本轮核心后接入 |
| 模板生成 | 模板字段填充、生成新的 Word、回到编辑区 | 后续 |
| PDF 与 OCR | PDF 阅读、文字提取、图片识别与校对 | 后续 |
| 批量文档处理 | 多文件摘要、字段提取、批量生成与结果列表 | 后续 |

摘要、翻译、润色是智能文档内部动作，不各自增加能力。编辑引擎、模型路由和 toolkit 是底层组件；知识库连接配置只有一份，独立问答与文档侧栏共同引用。功能完成后才登记可执行入口，避免先放不可用的占位能力。

## 5. 核心处理流程

1. **导入。** 桌面选择或拖入文件，创建文档会话；原件与工作副本分开管理。编辑器打开 DOCX 字节，问答绑定当前文件。
2. **提问。** 读取编辑器当前快照，包含未保存的人工修改。按选区/章节/全文范围组织正文；长文分段并标注实际采用范围，不能只截取开头却声称已读全文。
3. **检索。** 用户选用知识库时，先调用检索接口，保留返回的标题、片段与来源，再和文档内容一起交给现有模型服务。检索失败或无结果如实显示。
4. **建议。** AI 返回受支持的局部修改。用快照修订号、段落/表格位置和原文校验定位；重复文本不能依靠“只替换第一次”冒充准确选区。
5. **采用。** toolkit 在工作副本上生成候选，右侧展示差异。采用前核对当前正文是否变化，避免旧建议覆盖新输入；定位不唯一则保留建议，不直接改文件。
6. **保存与撤销。** 采用后标记未保存，用户点击保存才写目标文件；失败保留当前内容。AI 撤销需核对后续改动，不整份回滚覆盖新的人工输入。

文档与知识库内容是材料，其中夹带的指令不能扩大执行范围。用户指定外网 API 后，问答所需文本会发送到该服务；这不是完全离线 AI。此说明不新增逐次确认弹窗。

## 6. 新阶段安排与查收

以下阶段重新划分 AI 问答、AI 修改和知识库，取代旧 C002 的阶段表。旧 Fylar P0 不代表新 P0 完成。

| 阶段 | 实际工作 | 交付给用户查收的结果 |
| --- | --- | --- |
| P0：新编辑器验证 | 在隔离目录验证现有宿主加载、字体/WASM、中文输入、DOCX 打开/保存/重开、选区定位和 toolkit 往返；断网测试编辑；记录资源占用 | 可操作的验证入口、原件与结果、格式差异、实际新增体积和内存；说明继续采用该引擎的依据 |
| P1：工作台文档编辑 | 增加文档工作区、能力/岗位路由、文件桥接、最近文档、未保存状态和历史入口 | 在现有工作台打开并编辑 Word，保存后重开，切换岗位/文件不丢修改 |
| P2：AI 理解 | 接默认/指定外网模型，选区/章节/全文问答、来源定位、逐步输出、停止/重试和会话记录 | 对刚手动修改但未保存的内容提问，AI 使用新内容；网络失败后编辑仍可用 |
| P3：AI 修改 | 结构化建议、定位、toolkit 候选、差异、采用和撤销 | 自然语言修改指定段落，保住其他内容和人工输入，保存 Word 后能重开 |
| P4：外部知识库 | 对接一个实际服务；统一连接设置、检索、引用和独立能力；接文档侧栏 | 使用真实库检索并回答，能核对来源；配置为空、无结果和连接失败状态准确 |
| P5：回归与交付 | 代表性 DOCX、共享模块/岗位回归、资源测量、安装/复用/修复与离线安装 ZIP 更新 | 目标电脑可安装，编辑断网可用、AI 联网可用，兼容范围和交付清单明确 |

每阶段检验并提交 main 后继续。用户已决定知识库暂不接实际服务：P4 仅保留类型化检索接口与可扩展入口，不建立伪连接或无效能力。

建议用短文、长文、表格、图片、编号、页眉页脚和混合字体等代表性材料验证；真实文档不足时先使用合成样本，如实限制兼容性结论。整体工期在 P0 后再收敛，旧 Fylar 的 23–35 工作日不作为当前承诺。

- 服务端在 `dsh-capabilities/src/host` 增加文档会话、修改与知识库适配服务，注册到现有宿主；复用 `model-text.ts` 与共享执行记录。
- `core/model.ts`、组件登记、组合与岗位路由增加真实文档动作；管理页复用既有列表和编辑流程。
- 桌面增加文档专用桥接，复用现有来源检查，不向页面开放任意路径读写。会话和工作副本按现有本机数据根存放，退出/切换时保留需要恢复的内容。
- P0 核对插件构建、静态资源提供和 React 单实例。P5 同步安装、运行依赖检查与离线包制作；只有实际引入外部可执行程序时才登记 external-tools。
- 不部署模型，也不重复安装 Electron。此前约 200–500 MB 仅为新增文档组件、字体与缓存的预留估计，最终以实际包和运行测量为准；用户文件与缓存增长另计。
- 共享代码变更需回归会议、需求分析、文件搜索、能力编辑和岗位联动；未完成的其他事项原样保留。不读取或导出模型凭据，不提交用户文档、会话与安装二进制。
