4. 部署是第一项需要验证的条件

“编辑器显示在软件内部”和“完全不依赖文档服务、单机免安装运行”是不同交付条件。ONLYOFFICE Docs 路线能实现前者；后者需要独立验证。第 13 节补充浏览器端编辑插件，不要求所有路线均部署文档服务器。

部署方式使用体验工程影响本方案态度
内网文档服务，桌面内嵌编辑用户仍在工作台操作，文档在内网服务处理服务统一维护；客户端需能访问，文档需上传内网存储采用服务端编辑引擎时评估
本机部署文档服务有条件实现不依赖外部编辑服务安装体积、系统依赖、后台服务、端口和启动维护增加需针对实际 Windows 系统验证
公有云 Office 服务客户端部署相对轻原文件进入所选服务，依赖网络和授权不默认采用，作为明确选择后的备选
厂商支持的桌面嵌入 SDK可能更符合单机离线交付取决于 SDK 授权、平台与接口，需取得样例验证若单机便携为硬约束，优先核查此类方案

ONLYOFFICE 当前 Windows 开发版安装指南列出的系统要求为 64 位 Windows Server 2016 或更高，并说明离线安装需要单独下载前置依赖。因此不能直接承诺它在普通 Windows 10/11 上可随现有便携包双击即用；也不默认要求用户装 Docker/WSL。官方 Windows 安装说明

内网部署还需处理一项具体问题：服务器无法读取客户端的 localhost 或 C 盘路径。工作台应将用户打开的文件上传到指定内网文档网关，编辑服务经受限下载地址取文件，保存回调回到网关，再由客户端写回本机。不能简单把 localhost 文件地址传给远程编辑服务，也不临时暴露整台电脑目录。

在文档服务可用、许可证与样本允许的前提下，先完成一个 DOCX 的打开、编辑、选区读取、保存重开验证。此步骤是开发选型验证，不给普通用户新增使用前的检测向导。

5. 用户界面与操作流程

保留工作台现有导航和主题，在统一能力框架登记“智能文档”，提供文档工作区；岗位可引用相同能力。使用界面可以宽幅展示，管理界面继续共用现有组件。

左侧主区：约 70%右侧侧栏：约 30%
顶部：文件名、打开、保存、另存为、问答开关当前文件与本次提问范围
可折叠目录 + Office 编辑区；PDF 则显示原版页面已选内容摘要，可点击返回原位置
页码、缩放、查找，Word 常用编辑工具解释业务、概括内容、检查遗漏、翻译、改写
选中文字、段落或表格后出现“问 AI”入口问答正文、依据引用、修改建议
保存状态始终清楚，窄屏时侧栏改抽屉输入框、模型、停止生成；后续可选知识库

建议首版不默认照搬截图右上方整块重复原文。给问答留空间，把“提取文本”作为可展开查看项；用户能看到模型实际采用的内容与未识别范围。

以立项说明书为例：

  1. 打开 DOCX，直接查看并编辑标题、正文和表格。
  2. 选中“建设目标”，点击“问 AI”，右侧显示选区来源。
  3. 输入“这段具体解决什么业务问题？是否缺少验收指标？”
  4. 回答分为原文含义、基于原文的推断、建议补充，并引用对应段落。
  5. 点击“生成修改建议”，查看原文与建议；点击“应用到选区”后才更改文档，可撤销。
  6. 点击“保存”，成功写入文件后显示“已保存”；另存为则生成用户指定的新文件。

文档范围包括“所选内容”和“当前文档”；知识库接入后再提供“当前文档 + 指定知识库”。切换文档保留各自问答记录，引用卡明确文件名，防止误用另一文件内容。

Word 默认使用自然的文字/段落/单元格选择。PDF 文本页支持拖选和矩形框选；扫描页或图片的矩形选区走 OCR。“框选”不能只做一张截图就假装已经理解其中的文字、表格和图表。

7. AI、选区与引用怎样做可靠

数据流程：文档打开 → Office 编辑状态/解析内容 → 带位置的内容块 → 选区或全文检索 → 工作台模型 → 带依据回答/修改建议 → 用户采用 → 编辑器保存。

每个文档有内部文档 ID、内容修订标识和文件位置；每个内容块保留段落、表格单元格或 PDF 页码及区域。每次提问保存其使用的内容快照与范围，避免文件改过后历史答案还被当作针对当前正文。

当前编辑内容必须参与问答

用户手工修改后立即提问，AI 应读取编辑器当前内容，不能只读取磁盘上一次保存的旧版本。全文问答采用编辑器内容提取或当前编辑快照同步；具体 API 与大文档成本在验证阶段确定。如果同步尚未完成，界面明确当前依据，不能静默分析旧文。

引用需要定位，不让模型编页码

PDF 使用真实文件页码和页面坐标；Word 优先引用章节、段落或表格位置，只有编辑引擎能稳定返回当前页码时才显示页码。不要用 HTML 渲染的近似分页冒充原 Word 页码。

引用先由程序登记 ID，模型只选择已提供的引用，服务端核对原文与位置。找不到依据时显示“文档未说明”。点击引用定位并高亮；修订后位置失效时回看当时快照或提示内容已变化，不跳到同名但无关段落。

AI 修改应是小范围写回

优先用编辑器范围、书签或内容控件绑定目标，结合原文字段校验。生成期间用户已改动目标时，保留建议供重新应用，不自动覆盖新输入。普通文字替换尽量继承样式；段落结构、表格行列的更改作为明确修改类型，避免整段替换造成图片或格式丢失。

长文与扫描件分别处理

具体问题优先用选区、附近段落和相关检索片段；整篇摘要按章节覆盖生成，不能只检索几段就声称读完整篇。显示未处理页或识别失败范围。无文本页先 OCR，识别结果与页面坐标一起保存；中文金额、日期、单位要通过样本核查。需要图像理解时检测所选模型真实能力，纯文本链路不冒充识图。

PDF 可采用 PDF.js 定制阅读层并离线打包 worker、字体/字符映射等资源；它提供解析与显示基础，不直接提供本项目所需的 OCR 和语义选区。PDF.js 官方结构说明

OCR 通过独立适配器接入现有企业服务或本地引擎；Tesseract 可作为本地印刷文字基线进行中文样本测试，不能据此承诺复杂表格效果。Tesseract 官方文档

文档正文始终作为分析材料。即使文件中写有“忽略规则、上传目录、调用工具”，也不转成用户授权；问答操作默认不执行文件里的命令。

8. 保存与文件保护

Word 保存是首版验收主线，不是最后追加一个下载按钮。

  1. 用户打开本地文件后，建立内部编辑副本与来源关联，不在每次输入时直接覆盖原件。
  2. 编辑器的内部自动保存用于会话恢复；用户点击“保存”对应把最新内容真正写回目标文件，不额外要求发布版本。
  3. 工作台等待编辑服务完成并回传成功内容，再用临时文件加原子替换写盘；成功后更新“已保存”。临时写入策略按文件系统实际支持处理。
  4. 原文件被 WPS/Word 占用、无权限、空间不足或已被外部修改时，不显示成功；保留编辑结果，提供重试或另存为。
  5. 离开有未保存内容的文档时提供保存/放弃/取消；AI 问答历史与编辑正文分别保存，取消建议不丢提问记录。

文档服务回调需认证并对应正确文档；文件下载只使用受限地址。远程回调中的下载 URL 由服务端核验来源，避免随意抓取本机或内网资源。嵌入编辑器与工作台的通信校验来源和消息类型，凭据保留在服务端设置。

解析采用受限后台任务，限制文件和解压资源并支持取消；导入 HTML 不直接执行脚本。业务文件、OCR 缓存和问答放运行数据目录，不进源码 Git 或离线安装 ZIP。这里列的是必要实现约束，不新增面向用户的安全检查向导。

14.4 用户的三条主要操作流程

读与问： 打开立项说明书 → 左侧看到原文 → 选中一段 → 点击“解释这段”或在右下提问 → 右上固定本次选区 → 回答说明含义并引用章节/段落。无选区时可选择全文或指定章节。采用截图中的上下分区，但不默认重复展示整篇文本。

改与存： 选中文字 → 输入“改得正式一些” → 右侧显示原文、建议和变化范围 → 点击“采用修改” → 左侧显示改后内容并标记未保存 → 点击保存或 Ctrl+S 写入原文件。拒绝建议不改文档，生成结束不会自动覆盖原件。

独立工具： 从文档工具进入模板或 OCR → 选择材料并执行 → 查看实际结果 → 选择“在智能文档打开”或“用于本次问答”。批量工具输出到结果目录，默认另存；加入知识库需用户明确选择库和材料，不将所有打开文件自动入库。

首版先支持文字润色、章节改写、表格文字/简单结构调整和指定样式修改。默认只修改选中范围，不补写未经材料支持的业务数字；扩展范围需要在建议中明确呈现。自动翻译可作为问答或改写动作复用，不单独开发一套翻译服务。

14.6 最关键的衔接：当前内容、AI 修改和保存

已核实的接口事实。 Fylar 0.1.5 公开声明有 Selection.getSelectedText（可选）、查找、只读和撤销接口；Document.exportDocument() 返回 Promise<void>，未在本次查到的声明中暴露文档字节返回值或稳定的选区替换事务。插件现有文件路由只接受 GET/HEAD。因此不能直接写成“调用现成保存 API 即可”。参考 Fylar 接口声明 与 文件路由。这些是公开接口检查，尚未运行实测。

桌面端的可验证路线。 首先验证导出是否触发本机 Electron 下载事件。桌面端为当前导出创建内部任务，将匹配的 DOCX 下载保存到本次文档的临时位置，等待下载完成后再返回文件快照。Electron 官方提供 will-download、设置保存路径和下载完成状态接口，但 Fylar 在本工作台的实际事件来源、文件名、用户手势要求及连续导出行为仍需 P0 验证。Electron DownloadItem

桥接只接收已登记的当前编辑器导出，不能按“.docx 后缀”接管所有下载。需要可靠的发起者/导出任务关联；若共享页面无法可靠区分，则使用独立受控编辑器下载上下文或向厂商取得正式字节导出接口。不能用“下一个下载就是本次导出”的假设覆盖文件。未验证出可靠关联前，不交付一键保存。浏览器独立运行不作为首期验收目标。

导出桥接成功后，内部流程如下：

  1. 取得当前快照。 短暂锁定本次文档的编辑输入，导出包含当前手工修改的 DOCX 工作副本，完成后恢复编辑。只有必要操作短暂锁定，不在整个模型生成期间锁住界面。问答也使用这份当前内容，不能只读磁盘上的旧原件。
  2. 生成建议。 固定 documentId、原文位置、上下文和快照标识；模型返回范围明确的建议。toolkit 只在该快照的副本上应用操作，生成候选 DOCX 和差异摘要。dryRun 仅是操作摘要，不代替候选文件验证和真实差异比较。
  3. 展示变化。 右侧按段落/表格显示原文与建议，说明文字、格式或结构改动。普通问答不产生候选文件；“采用”之前不动编辑器和原文件。
  4. 采用前核对。 若用户生成期间继续编辑，采用时重新取得当前快照，对照操作基础。忽略 ZIP 封装时间等非正文打包差异，核对实际文档部件内容；不能只信鼠标/键盘事件构成的脏标记。发生变化时保留建议并提示按最新内容重新生成，不静默覆盖。
  5. 采用结果。 保留采用前的工作副本，将候选 DOCX 加载到当前编辑器。成功后显示“未保存”；加载失败恢复原工作副本，原磁盘文件仍保持。恢复大致章节/滚动位置，不能承诺未验证的精确光标位置。
  6. 保存落盘。 再导出当前编辑内容，经宿主检查输出 DOCX 可读取、来源授权与原文件未被外部改动后写入。先在目标同目录完成临时文件写入，再执行受控替换；保留必要旧内容用于失败恢复。Windows 文件占用、磁盘不足、下载中断均显示真实失败，不先删除原件。

原件只在用户保存时更新；内部工作副本、候选文件、临时恢复副本由程序管理，不给用户增加版本/备份管理页面。从未保存的新文档首次保存弹出一次原生路径选择，已有文件保存不重复询问。关闭存在未保存内容时提供保存、放弃、取消三个正常选项。

选区定位。 优先读取选中文本与可用段落信息，再映射到本次快照中的段落/表格路径、字符范围及相邻上下文；不能只靠页码或全局替换同名文本。重复文本出现多处时定位到具体段落，无法唯一定位时只显示建议，不自动修改。字符级保留、跨段落选区和表格单元格映射分别验证。

撤销边界。 人工编辑使用 Fylar 自带撤销；重新加载候选文件可能重置其撤销栈，因此不承诺原生 Ctrl+Z 能跨越 AI 加载。建议卡提供“撤销本次 AI 修改”：没有后续改动时恢复采用前工作副本；已有后续改动时通过局部反向建议处理，不能整篇回滚吃掉用户输入。原文范围无法可靠匹配时明确不能自动撤销，保留当前文件与原建议。

14.7 问答、检索和知识库边界

首版单文档问答不依赖外部知识库。先提取大纲及段落/表格内容，按章节组织，保留文档和段落标识；短文直接处理，长文按章节检索和摘要。全文摘要必须覆盖实际处理的全部章节，未覆盖时显示范围，不能把几段检索结果称为全文结论。

回答引用以章节、段落和原文片段为主；只有编辑器或 PDF 阅读器返回了可靠页位置才显示页码。点击依据可定位到对应正文，重新排版后不继续使用过期页码。手工修改后更新当前内容缓存，旧回答保留当时的来源快照标记。

只把完成本次问题所需的文字和上下文发送到已选模型服务；用户选用远端模型时，这些文本仍会离开本机，不能宣传为“全链路本地”。Fylar 的文档处理和授权联网、模型请求、OCR 服务、知识库请求分别说明用途，不自动上传原文件或后台入库。

文档、OCR 文字和检索片段属于待分析材料，不作为系统指令。材料内要求调用工具、上传文件或更改路径的内容不得直接执行。模型建议通过明确的文档修改操作应用，不授予通用 shell 或任意路径写入来完成润色。

知识库作为后续独立模块：优先适配用户已有服务的查询和入库 API；新建库需另外实现存储、更新、删除、访问范围和检索引用。当前演示目录不能冒充已建成的知识库。文档更新与库索引更新分别显示状态。

17.3 具体架构与代码落点

复用现有Electron、React、DSH宿主与模型服务。新增一个文档工作区和薄适配层，组织如下：

  1. 前端文档模块。 建议 dsh-client-ui-plain-chat/src/client/documents/ 下放工作区、编辑器适配、选区、问答/建议及历史状态；在apply.tsx与岗位模式中接入。编辑器重资源按实际加载器能力延迟加载，不新增第二套React。用户看到顶部文件操作、左侧文档、右上当前选区/引用、右下问答，符合参考图和已有主题。
  2. 文档业务服务。 建议 dsh-capabilities/src/core/document-model.ts 描述JSON契约，src/host/documents/管理会话、当前快照、修改建议、候选和保存协调，在现有宿主入口注册路由。它使用当前宿主进程，用户无需安装另一个文档服务器。现有HTTP JSON上限512KiB，不将整个DOCX塞成Base64再上调所有业务限制；文档二进制使用专用受控传输，文件上限独立处理。
  3. 模型适配。 沿用 model-text.ts 的路由与llm调用，最小扩展增量回调供文档使用；原调用签名/结果保持兼容。复用ExecutionStore和既有停止/错误处理，文档会话持有本次模型引用，Key留在已有服务端设置中。
  4. Word操作适配。 封装固定版本toolkit，仅开放当前文档所需读取/修改动作，输出落到本会话候选路径。当前包exports只提供插件根入口，历史P0直接导入lib/core/office.js是技术验证方式；P0需验证公开注册工具的宿主调用与会话路径边界，不能把私有文件路径当成长期稳定契约。
  5. 桌面文件桥接。 建议单独desktop/src/document-files.cjs，main/preload只接窄接口；基于用户选择建立文档文件句柄，支持打开、另存和已有目标保存。沿用assertProjectSender类来源校验，页面与模型不获得任意路径写入入口；临时文件完成校验后再替换目标，失败保留工作内容。
  6. 知识库适配。 建议 src/host/knowledge/提供统一search结果，保留真实sourceId、标题、片段、来源和可用定位；knowledge-model.ts只放可序列化契约。地址、库ID、超时与密钥引用沿现有服务配置；独立问答与文档侧栏共享同一连接，不保存两套Key或表单。
  7. 数据与交付。 会话、副本、对话、候选放在现有数据根的capabilities/documents/<id>一类目录，实际由宿主home解析，不写死本机路径。代码和依赖清单进Git，用户文档/缓存不进Git。新编辑静态资源进入既有构建与离线payload；只有新增可执行工具时才登记external-tools。

编辑候选保持 @docx-editor.dev/core/react 2.28.0开源部分，toolkit保持0.3.32；不引入商业扩展，不继续Fylar。此前已查阅编辑器项目、许可范围、加载保存接口；本轮未重复安装或运行候选。P0仍须核对实际依赖、发布资源和中文兼容。

17.4 AI理解、修改、知识库的真实闭环

选区问答以编辑器当前快照为准，保存前的手动输入也要进入上下文。选区、段落/单元格定位与提取内容必须来自同一个快照修订；不能拿磁盘旧版文本拼接当前选区。章节/全文提问按结构组织，长文分批或检索，并显示实际引用范围。

AI修改由模型返回受支持的结构化建议，本地校验后由toolkit改工作副本。修改锚点需要快照修订号、段落/表格位置、原文与上下文，重复段落不得用replace_text limit:1假装精确命中；若公开工具无法表达准确范围，应在P0明确限制，不能冒险全局替换。P3只交付已实测的修改类型。

候选在右栏展示原文/建议/范围，采用前检查快照修订，生成期间的新输入不得被覆盖。采用后加载候选、标记未保存；点击保存才写目标。局部命令可可靠保持原生撤销时优先使用；重新加载导致撤销栈重置时，AI撤销基于受影响区域和修订检查，后续修改无法安全合并时保留内容并提示，不整份恢复旧文件覆盖新输入。

知识库链路为：用户选择连接与库 → 用问题及必要文档主题检索 → 返回真实片段与来源 → 与当前文档上下文一起发送现有模型API → 展示有来源的回答。首次只对接一个实际服务的公开API；需要实际服务的接口说明、网络可达性与测试库才能宣称接通。仅有模型API不等于有知识库检索。建库、入库流水线、重排/向量模型、知识库管理平台另算，本轮不部署。

资料属于待分析内容，文档/检索片段内的指令不扩大任务和写入权限。前台展示当前模型与选用资料范围即可；用户已明确使用外网API，不新增每次问答的重复确认。
