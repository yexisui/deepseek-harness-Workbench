## 用户需求和范围

全局插件按层级折叠；新插件先进入未定义区；允许添加分组与模块标签、调整归属；区分功能分类和原始来源。插件管理移除 npm/Git 在线安装入口，改为 ZIP 为主、文件夹为辅的离线发布包导入。此次涉及真实分类和安装逻辑，不是纯界面预览。

## 已实施的界面

“设置 → 插件 → 插件列表”保持会话插件与全局插件分区。全局下面为未定义区、底层插件、工作台扩展；继续展开功能模块，最后显示插件卡片。默认折叠各级全局分组，记住浏览器内的展开状态。搜索支持包名、条目 ID、中文用途、来源与分类名称；搜索期间展开命中分组，清空搜索恢复原折叠状态。卡片显示完整身份、来源、运行状态及预设提供情况。

初始 178 个条目的映射来自本机运行清单与项目源码核查：官方底座 156，原 dsh-web 扩展 20，社区侧栏增强 1，本地普通聊天改造 1。一个安装包可能包含多个运行条目；178 不代表 178 个用户手动安装的包。

底层 156 个分为 12 个功能模块：框架与通信、模型、会话与存储、目标与计划、Agent 与上下文、终端与文件及任务、安全、工作区与附件及应用、技能与指令及预设、子 Agent 与工作流、网页能力、前端界面。工作台扩展按管理、开发、维护、资源、社区增强、本地改造归类。

“管理分类”支持新增、改名、排序、移动模块所属分组、删除分类并指定条目去向、单个或批量移动插件；保存和取消明确分开。分类存放在 dsh-data/plugin-management/classification.json，按模块名与稳定条目身份关联，升级、卸载后重新导入会保留同一身份的归属。新身份默认未定义；修改分类不改启停，也不改变来源标记。并发窗口保存使用版本校验，避免覆盖他人的修改。

## 离线安装和版本管理

“插件管理”显示“导入 ZIP 压缩包”和“选择插件文件夹”。导入先暂存并检查，再展示名称、版本、条目数、文件体积和依赖。确认后安装为工作台独立副本，原文件移动不影响使用。实际加载在重启后发生；待加载条目可在未定义区归类。

同名同内容不重复安装；版本变更或同版本不同内容必须确认替换。受管插件保留上一版本，可以回退；回退保留插件自己的业务数据，不承诺逆转插件运行时的数据迁移。启停继续使用现有 profile 覆盖机制。旧的本地链接、文件夹分别正确显示来源，历史 npm/Git 来源保留真实标签。

安装与卸载不调用 npm、pnpm、Git 或安装脚本，不会补下载依赖。创意工坊已有安装动作统一进入该离线安装服务；工坊资源库的导入与实际安装仍是两步，已安装插件的库副本可以更新，因为运行副本独立。

工作台组合包与官方底座不能通过此入口替换或卸载。已有非受管同名插件不会直接被覆盖，需要先迁移或卸载。底层包升级仍走项目维护流程。

## 支持的发布包约定

- ZIP 根目录（或唯一的外层目录）包含 package.json、已构建 JavaScript 入口和 dsh.bundle.patch 指向的 YAML 文件；也可直接选择同样结构的文件夹。
- package.json 需要有效包名和语义版本号；带浏览器部分的插件还需构建后的 client 导出。GitHub 源码 ZIP 通常需要作者先构建打包。
- 安装清单仅允许插入带稳定 ID 的本插件条目，不支持动态 YAML 表达式或修改其他模块。重复条目与当前清单冲突会拒绝安装。
- 官方 SDK、React 等共享依赖使用现有底座，并检查版本；其他运行依赖需要随包携带平铺的 node_modules，或由作者打包进构建产物。缺少依赖时直接给出错误。
- 检查 Node、平台/架构和声明的 Harness 版本；原生二进制需要匹配 dshOffline.platform、arch、nodeAbi。
- 不接收路径穿越、符号链接、Git 元数据和 .pnpm 存储目录；单包最多 2,000 文件/500 MiB、单文件 200 MiB。包内声明的安装脚本只显示已跳过，不执行。
