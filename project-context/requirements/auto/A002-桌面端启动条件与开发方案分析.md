## 为什么不能直接启动

桌面源码的 package.json 将 start 定义为运行 Electron。当前没有安装 Electron，因此未满足启动前提。

即使安装 Electron，main.cjs 还会检查自己的 Node 和 DSH 运行载荷；开发模式下路径固定从 desktop/resources/runtime 解析。目前这些文件不存在，程序将进入缺失运行时的错误流程，不会自动使用工作台根目录的 runtime。

## 现成构建脚本与用户目录要求的差异

原流程会在 desktop 内安装依赖，在 desktop/runtime 下安装宿主与 profile，再暂存到 desktop/resources/runtime。它面向完整桌面发行准备，还会下载 macOS 两种架构和 Windows x64 的 Node 载荷。

对于仅需本机 Windows 开发启动的目标，这些准备较重，且环境进入了源码目录。用户要求环境放在工作台根目录、与源码分开，因此不建议直接照搬这套流程。

桌面 profile 种子仍固定 dsh-web-all 0.3.19：
- 全新数据目录会使用该种子，需在后续装配中对齐目标版本。
- 若明确使用现有 dsh-data，代码会保留无桌面标记的用户自管 profile；不能误述为一定覆盖现有 0.3.23。

## 建议方案：独立环境的桌面开发启动

以下是建议，尚未实施或经用户确认：

1. 在工作台根目录建立独立的 runtime-desktop，安装桌面开发所需 Electron；暂不准备安装包工具链。
2. 给原桌面主进程增加可配置的开发运行路径，使开发模式使用现有 Node、runtime 内的 DSH，以及指定的 dsh-data。
3. 保留原桌面窗口、认证、日志和进程生命周期逻辑，使其自行管理专用端口上的 DSH 子进程；不伪装成安装了桌面应用，也不只是另开浏览器标签页。
4. 配置 Electron 的用户数据和日志目录，放在工作台内独立的 desktop-state，避免数据位置不清楚。
5. 增加工作台根目录的启动脚本或快捷方式，固定路径和 DSH_HOME。后续用户可以直接启动桌面窗口。
6. 验证窗口加载、profile 使用正确、关闭窗口仅清理它自己启动的进程；不干扰当前网页版。
7. 若开始修改业务插件，再另行建立本地插件构建与挂载流程；仅启动桌面壳仍会运行当前安装的 0.3.23 发布版插件。

采用此方案需要修改桌面开发启动逻辑。实现时应遵守源码仓库规则，并明确区分“外部开发运行路径”与“未来打包的内置载荷路径”。

建议目录职责：
- runtime：已有 DSH/pnpm。
- runtime-desktop：Electron 开发依赖。
- dsh-data：已有工作台配置、插件和会话。
- desktop-state：桌面窗口缓存、用户数据及日志。
- dsh-web-0.3.23：源文件。
上述新增目录尚未创建。

## 后续源码修改如何生效

- 桌面窗口、菜单和启动逻辑：运行修改后的桌面源码，按需重启桌面开发进程。
- 插件界面和业务逻辑：构建并挂载本地插件后才能生效；目前发布版插件不会自动读取旁边的源码。
- 分发给其他电脑：到交付阶段再制作安装包。

Electron 支持直接运行开发应用，无需先打包，见 [官方开发教程](https://www.electronjs.org/docs/latest/tutorial/tutorial-first-app)。
