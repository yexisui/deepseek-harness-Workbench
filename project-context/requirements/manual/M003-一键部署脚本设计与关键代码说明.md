## 1. 本次交付及使用顺序

交付两个文件：`一键部署.cmd` 和 `deploy.ps1`，放在**完整源码目录的上一级**，两者同级。源码目录可以改名；只有部分改动文件的归档目录不能代替完整源码。

第一次使用：

1. 将已修改的完整源码及这两个脚本放进同一工作台目录。
2. 连接网络，双击“一键部署.cmd”。有多个源码项目时，按提示输入编号。
3. 等待显示 `Completed`。关闭部署窗口后，双击生成的“启动桌面端.cmd”或“启动网页版.cmd”。
4. 第一次进入应用，在设置中填写模型供应商、模型名称和 API Key。
5. 在默认聊天输入框发送消息，确认模型能回复。安装检查通过本身不代表模型连接已经验证。

已有工作台部署或重新构建前，先正常结束正在进行的任务并退出桌面/网页宿主。脚本不会强制停止正在使用的应用。

| 工作台内的位置 | 用途 |
| --- | --- |
| 任意名称的完整源码目录 | 原始开发文件，要求已经包含桌面适配和直接对话改动 |
| 一键部署.cmd、deploy.ps1 | 双击入口和实际部署逻辑 |
| runtime-node | 官方便携 Node.js 与 npm |
| runtime | DSH、pnpm、npm 缓存、pnpm store、Node 下载缓存 |
| runtime-desktop | Electron npm 包、桌面程序和下载缓存 |
| runtime-dev | 开发依赖、构建镜像、辅助脚本、日志、备份、部署选择记录 |
| dsh-data | 原有模型配置、会话、插件与 web profile |
| chat-data | 普通聊天中性工作目录，由插件启动时创建 |
| desktop-state | 桌面状态与日志，由桌面应用启动时创建 |

环境安装在目录内，不修改系统 PATH，不内置模型密钥，不执行全局 npm 安装。当前基线限定 Windows x64，系统至少 Windows 10；ARM64、32 位系统会明确停止，不能把已有 x64 依赖直接视为经过验证的 ARM 环境。

## 2. 先从现有环境反推安装步骤

脚本不是照着项目根目录直接执行一次 `npm install`。现有工作台分成三部分：外部 DSH 宿主及 web profile、直接加载源码的 Electron 壳、需要独立构建的直接对话插件。因此先核对三个运行入口及实际版本，再将它们按依赖顺序组合起来。

执行顺序为：识别源码和系统 → 准备 Node → 安装 DSH/pnpm → 安装 Electron 本体 → 安装开发依赖 → 接入 web 插件 → 构建并登记直接对话插件 → 生成入口 → 检查。

开发依赖先准备好，直接对话插件随后在 `runtime-dev/builds` 中构建。正式 profile 链接到完整构建镜像中的插件目录，插件需要的预设、清单和构建输出也都保留在镜像里。

这意味着以后修改直接对话源码后，双击“重新构建.cmd”，再退出并重启宿主即可；桌面主进程源码改动则重启桌面生效。其他功能插件仍需建立各自的构建和接入流程，本脚本没有把整个项目所有插件都切换为源码开发模式。

## 3. 固定版本和锁文件

| 组件 | 固定版本 |
| --- | --- |
| Node.js | 24.13.1，win-x64 官方便携 ZIP |
| npm | 上述官方 Node ZIP 自带版本，不额外升级 |
| DSH | 0.1.5-rc.1 |
| pnpm | 11.24.0 |
| 工作台全家桶 | @linxin666/dsh-web-all 0.3.23 |
| Electron | 44.1.1 |
| tsdown / TypeScript | 0.22.2 / 5.7.3 |
| React / React DOM | 18.3.1 / 18.3.1 |
| lightningcss / Vitest / jsdom | 1.32.0 / 3.2.4 / 25.0.1 |

其余开发依赖按已核实的 `runtime-dev/package.json` 逐项固定，包括 SDK 和类型定义包。

仅写固定顶层版本，仍可能让新电脑解析到不同的间接依赖。因此 `deploy.ps1` 中的 `BaselineData` 保存了当前三个 npm 环境的清单和锁文件，以及 web profile 的公共依赖锁文件。它们经过 GZip 压缩后以 Base64 嵌入，保证移动到新电脑时只需携带两个部署文件。

该数据只包括公开软件包依赖，不包含当前用户的 profile 自定义项、模型配置、认证信息或绝对本地路径。旧直接对话链接也已从内嵌 web 锁文件中移除。

首次创建环境使用内嵌基线；已有环境保留自身锁文件，只合并本次管理的直接依赖版本。脚本不会强制覆盖用户额外添加的依赖，也不宣称任意被用户改动的旧环境能得到逐字节相同的依赖树。锁文件中的既有 registry 下载地址与完整性摘要会保留。

开发环境安装额外使用 `--legacy-peer-deps`：当前保存的开发 SDK 间接 peer 约束跨越不同 rc 版本，默认 npm 会尝试重新解析。该参数仅用于 `runtime-dev`，使这套构建依赖沿用已记录的锁文件；DSH 运行环境不套用该参数。三个环境都已通过离线 `npm ci --dry-run` 验证清单与锁文件一致。

## 4. 双击入口保持简单

```bat
@echo off
setlocal
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%~dp0deploy.ps1" %*
set "result=%errorlevel%"
pause
exit /b %result%
```

写法与原因：`%~dp0` 是 CMD 文件自身所在目录，双引号保护中文和空格路径；`%*` 允许手动调用入口时传入参数。立即保存退出码，避免后续 `pause` 影响最终结果。`-NoProfile` 不加载个人 PowerShell 配置；执行策略参数只用于该进程，不修改系统长期策略。交付版另外显示部署成功或失败信息。

PowerShell 主文件保存为 **UTF-8 BOM**，确保 Windows 自带的 PowerShell 5.1 正确读取中文入口文件名。CMD 内容保持 ASCII、CRLF 换行。

## 5. 自动定位源码，不记录固定文件夹名称

```powershell
$script:Root = $PSScriptRoot
$manifest = Join-Path $directory.FullName 'package.json'
$package = Read-Json $manifest
if ($package.name -eq 'dsh-web') { ... }
```

写法与原因：`$PSScriptRoot` 由 PowerShell 给出，代表主脚本所在位置。`Join-Path` 拼接路径，不依赖当前终端目录。脚本只枚举工作台的直接子目录，先按项目清单及桌面入口识别候选，再检查全家桶版本、桌面外部运行适配、聊天源码、共享构建配置及词典。

多个候选项目在部署时提示选择。选择结果保存在 `runtime-dev/deployment-selection.json`，只保存源码目录名；日常启动和构建在多个项目存在时复用这个选择。`lastRoot` 额外记录上一次工作台位置，用于判断是否需要修复链接，**不会用它替代当前 `$PSScriptRoot`**。

源码目录名参数只允许命中已发现的直接子目录，不能传入 `..` 指向工作台外部。环境根目录如果是目录联接或符号链接会停止，防止本应位于工作台内的安装实际落到别处。

## 6. Node 下载、校验和暂存

```powershell
$url = 'https://nodejs.org/dist/v' + $script:Versions.Node + '/'
Get-Download ($url + 'SHASUMS256.txt') $sums
$actual = (Get-FileHash -LiteralPath $archive -Algorithm SHA256).Hash
if ($actual -ne $expected) { throw 'Node.js ZIP SHA256 mismatch' }
```

写法与原因：版本组成官方发布 URL，校验值从该版本官方摘要文件中按完整 ZIP 文件名精确匹配。`Get-FileHash` 对实际下载字节计算 SHA256；不匹配时直接停止，不执行解压。摘要与 ZIP 均通过 HTTPS 下载，这里并未额外实现 GPG 签名验证。

下载先写 `.partial` 文件，成功后改为最终名称；已有缓存通过校验则复用。最多重试三次。解压发生在独立暂存目录，确认 Node 和 npm 入口存在后才接入 `runtime-node`。原有 Node 目录需要替换时保留在下载目录的 `previous-node-*` 下，不直接删除。

已安装的本地 Node 版本正确且必要文件存在时直接使用。`-Repair` 可以要求重新校验下载和准备 Node。

## 7. 统一使用本地工具和缓存

```powershell
$script:Node = Join-Path $script:Root 'runtime-node\node.exe'
$env:DSH_HOME = Join-Path $script:Root 'dsh-data'
$env:DSH_DESKTOP_NODE = $script:Node
$env:PATH = (Join-Path $script:Root 'runtime-node') + ';' + $env:PATH
```

写法与原因：Node 使用明确的本地可执行文件路径；PATH 前置本地 Node，让依赖安装脚本和应用子进程也优先使用它。环境变量只影响当前进程及其子进程，不写入 Windows 系统设置。

npm CLI、pnpm CLI、DSH CLI 都由这个 Node 直接执行。npm 缓存、pnpm store、Electron 缓存和 XDG 缓存/数据目录也指向工作台。第三方依赖在构建中使用的系统临时目录或系统级编译器不等于目录内运行环境，不能承诺每个第三方程序都完全不使用系统临时文件。

```powershell
Invoke-Tool $script:Node @($script:Pnpm, 'add', '@linxin666/dsh-web-all@0.3.23',
    '--save-exact', '--allow-build=cloudflared', '--allow-build=cpu-features',
    '--allow-build=node-pty', '--allow-build=ssh2') $script:Profile
```

写法与原因：参数用数组逐个传入，路径中的空格不会被拆成多个参数，也不拼接成待执行的 shell 字符串。四个构建许可明确限定 pnpm 安装中需要运行构建脚本的依赖，避免等待交互选择。npm 管理的三个独立环境则按照各自锁文件执行正常安装脚本。

本地 DSH 的 Windows 插件命令通过 shell 转发 pnpm 参数。为了可靠处理本地插件路径，脚本直接运行 pnpm，并另外合并 `dsh.profile.bundles`；初始化辅助文件仍调用该版本 DSH 的 `initProfile`，保留已有配置。

## 8. Electron 包与程序本体分别检查

```powershell
Invoke-Tool $script:Node @((Join-Path $script:Root 'runtime-desktop\node_modules\electron\install.js'))
Require-File $script:Electron
Invoke-Tool $script:Electron @('--version')
```

写法与原因：安装 npm 包不等于 Electron 可执行程序已经准备好。固定版本的 `install.js` 会复用已有本体或下载缺少的本体，并使用包内校验信息；随后确认 `electron.exe` 存在且版本命令能执行。

桌面入口启动前移除进程内的 `ELECTRON_RUN_AS_NODE`，并设置 `DSH_DESKTOP_DEV_ROOT` 和 `DSH_DESKTOP_NODE`，让现有桌面适配加载本地 Node 和既有 web profile。网页版保持终端连接，显示应用实际访问地址，通过 Ctrl+C 停止服务。

## 9. 构建镜像、重复执行和迁移

构建脚本收集直接对话插件、共享构建文件和使用到的俄语词典，排除 `node_modules`、`lib` 和 `.git`。输入文件内容与开发锁文件一起计算摘要，以此查找可复用的构建镜像。

```javascript
const result = spawnSync(process.execPath, [tool], {
  cwd, stdio: 'inherit', windowsHide: true
});
if (result.status !== 0) throw new Error('Plain-chat build failed');
```

写法与原因：构建子进程使用当前 Node，工作目录是镜像中的插件目录。`stdio: 'inherit'` 将构建信息传回部署日志；明确检查退出码。镜像位于 `runtime-dev` 下面，模块解析可找到同一个开发环境中的依赖，无需在源码目录安装依赖。

构建成功后为入口产物和预设记录内容摘要。下次输入不变、输出校验也通过就复用；输出缺失或被改坏则新建镜像重建，旧镜像保留。只有成功完成的镜像才用于接入。

```text
link:../../../runtime-dev/builds/<摘要目录>/packages/dsh-client-ui-plain-chat
```

写法与原因：该链接相对于 `dsh-data/profiles/web`，通过三个 `..` 回到工作台，再找到源码外的完整插件镜像。它不是写死的盘符或用户名。整个工作台移动或源码改名后，重新部署会先修复旧聊天依赖，再接入当前镜像；检测到工作台根位置变化时给 pnpm 增加 `--force`，重建必要安装链接。

旧备份、旧 Node 和旧构建镜像不会自动清理，因而可能逐渐占用磁盘。它们用于复查或恢复；脚本不会猜测哪些用户历史文件可以删除。

## 10. 配置备份与失败处理

```powershell
Backup-File $file
$manifest = Read-Json $file
Set-Field $profileObject 'bundles' $bundles
Write-Json $file $manifest
```

写法与原因：读取现有对象、只合并需要的属性，再写回，避免用固定模板替换整个用户配置。写入前将原文件按工作台相对路径存入本次备份目录；同一次运行中每个文件只备份第一次看到的版本。写入使用临时文件，再替换最终文件。

部署前备份 web profile 的清单、锁文件、工作区配置、`.npmrc` 和插件覆盖配置（存在时）；独立 npm 环境的清单和锁文件也会备份。备份可能包含用户自己写入的私有配置，和 `dsh-data` 一样只在本地保存，不应随公共部署文件分发。

不会读取或重写模型凭据与会话存储。直接对话插件本身启动时会安装其所属的 `workbench-chat` 预设，这是已有插件行为，不是把整个预设目录或用户会话恢复成默认值。

```powershell
& $Exe @Arguments
$code = $LASTEXITCODE
if ($code -ne 0) { throw "Command failed (exit $code)" }
```

写法与原因：PowerShell 的 `$ErrorActionPreference = 'Stop'` 不足以可靠拦截外部程序的非零退出码，所以必须额外检查 `$LASTEXITCODE`。实际封装还将输出附上时间与步骤写入日志，并将原生 stderr 作为诊断输出处理，防止正常构建警告被误判为安装失败。

日志位于 `runtime-dev/logs/deploy-日期-标识.log`，备份位于 `runtime-dev/backups/deploy-日期-标识/`。系统和源码预检查发生在安装开始前，预检查失败仅在窗口显示原因，不创建运行环境。独占文件锁防止同一个工作台同时执行两次部署或构建。

失败后立即停止，不继续显示成功，也不自动回滚整个用户 profile。已经完成的下载、安装和备份保留，下次从目录中的实际状态继续。若系统缺少原生依赖需要的 Microsoft C++ Build Tools、Python 或运行库，错误窗口会提示检查；脚本不自动安装需要管理员权限的系统组件。

## 11. 日常入口与可选参数

| 入口/模式 | 行为 |
| --- | --- |
| 一键部署.cmd / Deploy | 安装或补齐整套环境，构建聊天插件，更新入口并检查 |
| 启动桌面端.cmd / Desktop | 使用本地 Node 和外部运行环境启动桌面源码 |
| 启动网页版.cmd / Web | 启动同一 web profile 的网页版，保持终端可见 |
| 重新构建.cmd / Build | 重新检查并构建直接对话镜像、更新链接；复用已有开发依赖 |
| Inspect | 只检查系统和源码识别，不安装、不写配置 |
| Check | 只检查已部署版本、文件、登记及入口，不发送模型请求 |
| -SourceName | 从已识别的源码子目录中指定一个 |
| -Repair | Deploy 模式下重建 Node，npm 使用 ci，pnpm 使用 force；修复依赖文件损坏 |

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1 -Mode Inspect
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1 -Mode Check
```

写法与原因：在工作台目录执行，分别检查源码条件和安装结果；`.\` 明确指当前目录中的主脚本。普通双击无需输入这些命令。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1 -Mode Deploy -SourceName '我的 源码' -Repair
```

写法与原因：单引号保留源码目录名中的空格；指定来源可避免多项目选择。`-Repair` 会重新创建受 npm 管理的依赖树，不清除源码、模型配置或会话；正常部署优先用 `npm install` 复用锁文件和完整依赖。

## 12. 实际验证范围

已验证：

- Windows PowerShell 5.1 主脚本及生成的兼容启动脚本解析。
- 内嵌基线解压、固定版本读取、三个 npm 环境的离线 `ci --dry-run` 清单与锁文件校验。
- 中文与空格路径的源码发现、多个源码显式选择、非法目录选择拒绝、缺少必要改动时停止。
- 自定义 profile 字段保留、插件登记重复运行不重复追加、原文件备份。
- 本地 Node 路径设置、启动入口生成和原生命令失败传播。
- 隔离目录中使用当前真实源码完成直接对话插件构建，pnpm 建立本地链接；未修改正式 profile。
- 未改源码时复用构建；构建输出损坏时重新生成；修复后的构建再次执行可以复用。

未验证：新电脑首次联网下载全部依赖、Node 官方下载链路的完整运行、整套环境移动到另一台机器后启动、真实模型回复。现有机器的 Electron/直接对话历史验证见 M002、A004，不能代替本脚本的一次空目录完整安装验收。

迁移已有 `dsh-data` 时，原应用若使用系统绑定的凭据加密，新电脑可能需要重新填写 Key；部署脚本不导出或解密凭据。

## 2026-10-10 补充：已有工作台的便携环境补齐

旧桌面环境使用系统 Node，若缺少 runtime-node，可在工作台根执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1 -Mode Bootstrap
```

命令使用 Bootstrap 模式，仅安装/复用固定版本便携 Node/npm、补齐缺失入口并检查当前安装；不重装依赖、不重新登记 profile，已有启动脚本与用户数据保留。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1 -Mode Check
```

Check 只验证安装状态，不下载或写业务配置。完整新环境安装仍使用 Deploy；无需为了仅缺便携 Node 而执行全量重装。
