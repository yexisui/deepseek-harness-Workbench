# 工作量估算表生成

根据用户提供的项目介绍/需求，拆解出功能项并逐项评估开发工作量，输出与模板文件
`assets/工作量估算表-模板.xlsx` 结构完全一致的工作量估算表。

## 模板与公式机制（先理解再动手）

模板共 2 个 sheet：

- **工作量汇总表**（样式固定，与交付示例完全一致，含颜色/单元格数量）：
  - 固定 **3 行 × 3 列** 基础结构，**无合计行**：
    - 第 1 行：A1:C1 合并，项目名（不加后缀），浅蓝 `#CCFFFF` 底 + 宋体 14 加粗 + 细边框 + 居中换行，行高 47.25
    - 第 2 行：表头 `费用项 / 数量（人月）/ 备注`，同样 `#CCFFFF` 底 + 宋体 11 + 细边框 + 水平居中，行高 21.75
    - 第 3 行起：每个费用项一行 —— 费用项 = **部分名**（不拼接项目名前缀，`part_name` 可指定，如示例的 `CUD`）、
      数量（人月）引用明细表「小计：人月」行 K 列（数字格式 `0.00_ `，宋体 12 加粗）、
      备注 = `1人月按照21.75人天计算；`（仅首行，宋体 12）
  - 列宽 A=19 / B=12.83 / C=26.17，行高 47.25 / 21.75 / 21.75，数据行宋体 11、无填充
- **AI部分明细表**：唯一一张明细表，所有模块/功能项都在这张表里（样式保持不变：
  灰色 #C0C0C0 表头、系统/估算项/功能分层、单列编码人天手填、其余公式联动）：
  - 第 1–2 行表头，其中第 2 行是**比例行**：需求0.2 / 设计0.15 / 编码0.4 / 测试0.15 / 管理0.1（合计1）
  - 数据行为：序号 / 系统 / 估算项 / 细分项 / 功能 / 需求人天 / 设计人天 / **编码人天** / 测试人天 / 管理人天 / 合计 / 功能概要
  - 底部「小计：人天」（各列 SUM）+「小计：人月」（各列 ÷21.75）

**公式机制（必须保留，不能改成数值）**：

- 需求/设计/测试/管理人天 = 比例 × 编码人天，公式形如 `=$F$2*H3/$H$2`
  （即需求=0.5×编码、设计=0.375×编码、测试=0.375×编码、管理=0.25×编码）
- 行合计 K 列 = `=SUM(F3:J3)`，一行合计人天 = **2.5 × 编码人天**
- 小计人月 = 小计人天 ÷ 21.75（1人月=21.75人天）
- 汇总表 B 列（数量（人月））= 引用明细表「小计：人月」行 K 列；**汇总表只有 3 行（标题行 +
  表头行 + 费用项行），没有合计行**，总人月直接看明细表底部的「小计：人月」；不含单价/金额列

因此**只有「编码人天」列是手动评估值**，其余列全部由公式联动。跟用户说明这一点：
后续要调整工作量，只改「编码人天」列即可，其他列会自动重算。

## 公共部分（默认不包含）

模板中「**域登录与安全**」「**系统日志管理**」「**系统安全**」3 个模块为公共部分
（域登录验证/加密验证/数字证书/4A认证/用户操作日志/异常日志/配置文件加密/服务器漏洞整改/
证书域名/服务器搭建部署/UAU角色配置，共 11 项，合计约 21.5 编码人天 / 2.5 人月）。

**默认不纳入估算**（`include_common` 缺省为 false，脚本不追加）。仅当用户明确要求
包含公共基础设施工作量时，spec 显式设 `"include_common": true` 才会追加到
AI部分 明细表末尾，且每项编码人天自动限制在 0.5~3 之间（脚本自动限制并校验）。

## 工作流程

### 1. 收集输入
读取用户提供的项目介绍/需求。若输入信息不足（缺项目名、缺功能范围），先向用户索要
关键信息，而不是硬编。

### 2. 先问用户两个参数（目标总人月、单价）
**动手拆分前，必须先问用户**：

> 请问这次工作量预估有没有目标总人月要求？（没有的话我就按功能拆解自行评估）

- **有目标 T**：记下 T，生成草稿后按比例缩放各项编码人月，使总人月 ≈ T
- **没有**：按默认区间 20~30 人月处理——草稿在区间内保持原样，低于 20 提到 20，
  高于 30 压到 30（详见步骤 5），生成后如实汇报并主动询问是否需要调整到指定人月

**单价无需询问**——汇总表只含「费用项 / 数量（人月）/ 备注」三列，不含单价与金额列，
生成时不用问单价；如需金额，由用户自行按 单价×人月 计算。

### 3. 需求拆解
把需求直接拆成 **模块**，模块下拆 **功能项**，全部写入唯一一张「AI部分」明细表
（汇总表只此一行、无合计行，不按部分拆分多个工作表）。模块按自然功能域划分
（如「智能审查引擎」「数据接入与识别」），规模小也可以就 1 个模块。

**只输出AI部分工作量**：明细表只有一张「AI部分」，哪些功能属于AI范围，统一按
「**AI能力闭环**」口径判定（用户要求区分AI/非AI时同样只输出AI部分，非AI部分不生成明细表）。

**AI范围判定（统一按「AI能力闭环」口径执行，不得临场判断）**：AI不是孤立的模型调用，
而是一条「输入准备 → 模型处理 → 输出交付 → 支撑调优」的完整链路。**凡是直接围绕AI能力
形成闭环的环节（无论前置准备还是后续输出）都纳入AI估算**；与AI闭环无直接绑定关系的
通用业务工程**不纳入估算**。

**关键判定（「专门」二字）**：去掉该功能后，AI能力是否还能完整运转？
- 该功能**专门为AI服务**（AI依赖它作输入或输出，去掉后AI无法运转或失去意义）→ 归AI
- 该功能是**独立业务能力**（即使AI会用到，去掉后依然独立存在、有独立价值）→ 归非AI，不估算

- **归 AI（纳入估算）**——AI闭环全环节：
  - 输入准备：专门为AI提供输入的数据获取、解析、结构化、规则/知识库、触发条件
    （如附件解析、业务数据识别提取、判断规则库）
  - 模型处理：语义理解/意图识别/信息抽取、内容生成（结论、意见、话术）、
    基于非结构化文本的智能判断、智能对话交互
  - 输出交付：结果格式化、回写、触达、留痕、复核
  - 支撑调优（跟随AI主体）：大模型接口集成封装、测试用例集、准确率/性能调优、
    并发保障、异常兜底
- **归 非AI（不纳入估算）**——与AI闭环无直接绑定的业务工程：
  - 流程环节改造、表单/字段/字典改造
  - RPA自动化（数据抓取/代填/预警）
  - 独立数据展示（数据看板/报表/统计/图表）
  - 权限角色、文档、与AI闭环无关的系统集成联调
  - **公共部分**（域登录与安全/系统日志管理/系统安全）默认不包含
- **混合项处理**：一个功能项同时含工程+AI时按「核心价值/主体用途」归属；拆得开就拆
  （如第三方数据查询对接→AI数据准备，查询结果图表→非AI展示，图表部分不估算），
  拆不开按主要工作量所在归属
- **同一功能只拆一份、只归一边**：不要从AI视角和业务视角各拆一个功能项，
  同一功能无论怎么归类都只保留一份

**功能项必须细分——绝不能把一个需求整体直接当成一个功能项**：

- 一个需求（功能点）拆到**原子任务粒度**：以「不能再拆出一个可独立交付的任务」为准，
  通常 3~8 项；拆不出 2 个说明对需求理解不够，先回到需求梳理，而不是硬编成 1 项
- 功能项粒度：一个功能项 ≈ 一个明确的开发任务，细分评估时编码人天通常 **2~6 天**，
  个别复杂项 ≤8 天；预评估超过 8 天的功能项必须继续拆分
- **细分只覆盖原需求范围**：不新增原需求之外的工作项（数据准备/清洗/标注、培训、
  运维支持等一律不补）；「调工作量」阶段（步骤 5）可以把细分项的评估值按复杂度上调，
  但那是调值，不是加项
- 常用拆解维度（按需求性质组合，不必全用）：
  1. **规则/数据准备**：规则梳理与定义、数据项与特征定义、字典/枚举定义
  2. **核心功能开发**：核心算法/引擎/接口实现（这是功能项的主体，可拆多个）
  3. **输出与展示**：结果组装、格式化输出、页面展示
  4. **集成联调**：与外部系统/流程集成、接口联调
  5. **测试与调优**：准确率/性能测试、规则迭代调优
  6. **异常与兼容**：异常处理、存量数据/流程实例兼容
- 示例：需求「附件内容识别」应拆为「多格式附件解析组件（6）」「附件对接获取（3）」
  「附件内容语义识别（6）」「附件解析异常与性能处理（3）」4 项，而不是 1 项
  「附件内容识别（14）」
- 每个功能项给出：功能名（可多个连续子项共用）、说明（一句具体做什么）、编码人天；
  备注列默认留空，不要把需求编号、场景说明写进备注
- 说明要具体，避免「实现相关功能」这类空话

### 4. 评估编码人天（唯一手动列）
在细分后的功能项上逐项评估「编码人天」。功能项细分后单项目变量级为：
**2~6 人天/项**（数据准备/页面/字典/配置类 2~3，算法/引擎/接口类 4~6，个别复杂项 ≤8），
简单项可 1 人天。评估时考虑：功能复杂度、涉及模块数、联调/集成工作量、是否涉及第三方
对接。宁可在细分项上保守，不要虚高。

注意：细分后总人天往往比粗粒度评估更高——这是正常的，细分会暴露粗粒度掩盖掉的工作量
（测试调优、兼容处理、联调、异常处理等），如实汇报即可。

### 5. 处理总人月（有目标按目标，无目标按默认区间 20~30）
- 草稿总人月 = Σ编码人天 × 2.5 ÷ 21.75
- 先定目标 T：有目标取用户给的 T；无目标时草稿在 20~30 内 → 不调整；草稿 < 20 → T=20；
  草稿 > 30 → T=30。目标编码人天 = T×8.7
- **调整方式（严格按顺序，且不超出原需求范围）**：
  1. **细分到不能细分**：确认原需求已拆到原子任务粒度（每需求 3~8 项），细分本身会
     显式化一部分隐藏工作量
  2. **调整工作量**：在细分项上按功能复杂度、联调/兼容/异常场景逐项合理调整编码人天
     （单项目合理区间 4~12 天），使总量逼近目标
  3. **禁止**：新增原需求之外的工作项（数据准备/清洗/标注、培训、运维支持等一律不补）；
     对全部项机械乘同一系数
  4. 需要缩小时：合并过细项、压缩项值，不砍需求
- 调整后重算总人月；若与目标/区间仍有偏差，如实说明实际达成值与原因

### 6. 生成 JSON 规范并运行脚本
把拆分结果写成 JSON（schema 见下），运行：

```bash
python <技能目录>/scripts/build_estimate.py --spec spec.json -o 工作量估算表-<项目名>.xlsx
```

- 输出文件默认保存到当前工作目录；先问用户希望的保存位置/文件名，或直接按上面规则命名并告知
- 依赖：python3 + openpyxl。先检查 `python -c "import openpyxl"`，缺失则
  `pip install openpyxl`

### 7. 校验并汇报
脚本会自动核对公式/小计范围/汇总引用并打印统计。向用户汇报：

- AI部分：功能项数、Σ编码人天、合计人天、人月；各模块分组统计
- 总计：总人月
- 若按默认区间调整过，说明调整前后的人月变化
- 提醒：表格中只有「编码人天」列可手动修改，其余为公式；1人月=21.75人天

## JSON 规范（脚本输入）

```json
{
  "project_name": "XX智能审查项目",
  "part_name": "CUD",
  "modules": [
    {
      "name": "智能审查引擎",
      "items": [
        {"func": "审查规则库搭建", "desc": "梳理审查规则并转化为结构化规则库（规则项、阈值、提示语）", "coding_days": 4, "remark": ""},
        {"func": "审查结论生成算法", "desc": "实现自动审查与结论生成，支持通过/驳回/需人工复核三种状态", "coding_days": 6},
        {"func": "审查结果格式化输出", "desc": "审查结论结果组装、格式化输出", "coding_days": 3}
      ]
    },
    {
      "name": "数据接入与识别",
      "items": [
        {"func": "多格式附件解析组件", "desc": "Word/Excel/PDF多格式解析组件开发", "coding_days": 6}
      ]
    }
  ]
}
```

说明：
- 输出固定 2 张表：**工作量汇总表 + AI部分明细表**（所有模块合并进这一张表；
  汇总表固定 3 行结构 —— 合并标题行（项目名）+ 表头行 + 费用项一行，**无合计行**）；
  旧格式 `"parts": [{"name": ..., "modules": [...]}]` 仍兼容，多个部分会合并为
  一张 AI部分 明细表
- `part_name` 可选：**费用项名称**（同时作为明细表 sheet 名），默认 `AI部分`；
  需要和目标示例一样显示特定费用项（如 `CUD`）时指定即可
- 汇总表不含单价/金额列，spec **不需要** `unit_price`（旧 spec 保留该字段会被忽略，仅兼容）
- `func` 相同的连续功能项会在表中合并单元格（D 列）
- `coding_days` 是唯一手动评估值，其余人天由脚本按模板公式生成
- `remark` 可选，写入备注列；**默认留空**——只有真实业务约束才写（如「后期阶段实施」），
  不要写需求编号映射、场景说明等描述性内容
- `include_common` 可选，**默认 false**：不追加公共部分（域登录与安全/系统日志管理/系统安全）；
  仅当用户明确要求包含公共部分时才设 `true`（追加到第一个明细表末尾，每项人天限制在 0.5~3 之间）

## 注意事项

- **不要**把公式列写成数值：需求/设计/测试/管理人天、行合计、小计、汇总引用全部必须是公式
- **汇总表样式固定**：浅蓝 `#CCFFFF` 表头/标题（宋体）、3 行 × 3 列基础结构、**无合计行**，
  颜色/单元格数量/列宽行高与模板（及交付示例）完全一致；不要自行添加合计行或改颜色
- **汇总表不含单价/金额**：只输出费用项、数量（人月）、备注三列，生成时无需询问单价
- **不要**自己拼 Excel：一律通过脚本生成，保证与模板样式/公式一致
- 明细 sheet 固定一张，名称 = **费用项名称**（默认 `AI部分`，`part_name` 可指定，脚本自动处理非法字符）
- **只输出AI部分**：唯一一张明细表即「AI部分」，按步骤 3 的「AI能力闭环」口径判定；
  非AI业务工程（流程改造/字段改造/图表展示/RPA等）不生成明细表；
  公共部分默认不包含（`include_common` 默认 false）
- 公共部分仅在用户明确要求时才设 `include_common: true`，每项编码人天必须落在 0.5~3 之间
  （脚本强制限制并校验，超出会报错）
- 无目标人月且草稿总量不在 20~30 人月内时，通过**原需求细分到极致 + 逐项调整工作量**
  调到区间边界（20 或 30），禁止新增需求外工作项、禁止按比例整体缩放；
  如实说明调整前后的人月变化
- 若用户后续想改某个功能项的工作量，指导其只改表中「编码人天」列
